# Prior art and dependency candidates

Dated pre-implementation source research for README/design authors, observed 2026-10-01 UTC. Versions, source details, activity, and metrics below retain those original observations. Installation, compilation, and runtime compatibility testing were outside this study. The [README](../../README.md) and [architecture report](../../reports/TUI%20frame%20architecture%20research.md) describe the selected implementation and current contract. GitHub stars and activity are observations, not compatibility evidence. GitHub `pushed_at` is repository activity, not necessarily activity in the named submodule. An absent GitHub release is not an absent Go module tag.

## Which prior art matches one external TUI inside an information frame?

### Takeaway

Existing multiplexers establish the necessary PTY → terminal-state → composite-screen architecture. The closest directly embeddable Go project found is `tvxterm`, but its small emulator and framework-owned input are poor evidence for arbitrary-TUI transparency. A purpose-built library can omit panes/session management while retaining terminal emulation and protocol mediation. [tmux architecture](https://raw.githubusercontent.com/tmux/tmux/1536b7e206e51488c37379df22b8c58ef3febc28/presentations/tmux_asiabsdcon11.pdf), [tvxterm](https://github.com/blacknon/tvxterm).

### Cited Findings

| Prior art | Relevant behavior | Reuse assessment |
| --- | --- | --- |
| [tmux](https://github.com/tmux/tmux/wiki/Control-Mode) | Control mode exposes raw pane output through escaped `%output`, commands, asynchronous notifications, capture/inspection, and flow control. Clients still interpret the child's terminal stream. | Strong architectural reference; a separate C application/server, not an embeddable Go library. An external tmux backend adds a daemon, command protocol, and tmux-specific terminal identity. |
| [GNU Screen overview](https://www.gnu.org/software/screen/manual/html_node/Overview.html), [captions](https://www.gnu.org/software/screen/manual/html_node/Caption.html), [hardstatus](https://www.gnu.org/software/screen/manual/html_node/Hardstatus.html) | VT100 plus additional ECMA-48 terminal functions; caption can be always visible even with one window; per-window hardstatus exposes information surrounding a running application. | Close user experience prior art. [Command characters](https://www.gnu.org/software/screen/manual/html_node/Command-Character.html) normally intercept Ctrl-A; that default differs from this request. |
| [Zellij plugin events](https://zellij.dev/documentation/plugin-api-events), [commands](https://zellij.dev/documentation/plugin-api-commands) | Plugins subscribe to pane metadata including title, position, dimensions, command/focus, lifecycle and input events; commands expose terminal actions. | Good metadata/event API precedent; a Rust workspace application and plugin host, not a Go dependency. |
| [TUIOS](https://github.com/Gaurav-Gosain/tuios), [current module](https://github.com/Gaurav-Gosain/tuios/blob/main/go.mod) | A current Go multiplexer/window manager consumes Ultraviolet, `x/xpty`, and `go.mitchellh.com/libghostty`. | Concrete adoption signal for this layered stack, not proof its particular forwarding policy meets our contract. |
| [3mux](https://github.com/aaronjanse/3mux), [module](https://github.com/aaronjanse/3mux/blob/master/go.mod) | Go multiplexer with its own terminal implementation and an `aaronjanse/pty` fork. Current module still declares Go 1.14 and old dependency versions. | Architecture/source reference; importing a full application or its internal terminal stack would couple unrelated pane/session concerns. |
| [tvxterm](https://github.com/blacknon/tvxterm) | PTY and generic-stream backends, `tview.Primitive`, title hooks, screen/scrollback state, keyboard/paste/focus/mouse handling. Documentation explicitly says emulator is small and some terminal features remain incomplete. | Closest library prior art. Its [module](https://github.com/blacknon/tvxterm/blob/master/go.mod) pulls SSH/NFS/PKCS11-related dependencies and tcell v2; not an attractive default for a narrow frame library. |

### Inferences

- The intended distinction is a concise single-child library with no default keybindings, rather than a new multiplexer application. That still needs an emulator; a PTY by itself provides a byte transport, not a screen/cursor/mode model. [creack/pty](https://github.com/creack/pty), [x/vt terminal interface](https://github.com/charmbracelet/x/blob/main/vt/terminal.go).
- Zellij's distinction between observed state and event subscriptions is useful for the host's information frame, without copying its workspace/pane API. [Plugin events](https://zellij.dev/documentation/plugin-api-events).

### Gaps

- GNU Screen's current release/activity/license metadata was not captured; the official manuals were accessible with curl after the browsing tool timed out. No inference about its current release cadence is needed.
- No inspected project establishes byte preservation, arbitrary escape-sequence support, or complete metadata access for every child application.

## Which dependencies are suitable, and where are the terminal contract gaps?

### Takeaway

For a Unix-first build, `creack/pty` is the most established direct transport candidate. `go.mitchellh.com/libghostty` offers the strongest inspected terminal-state/protocol surface, at the cost of CGO/native tooling and an unstable Go API. The pure Go `x/vt` alternative has decisive modern keyboard-negotiation and mouse-encoding omissions; raw input relay alone does not repair them. [PTY](https://github.com/creack/pty), [libghostty binding](https://github.com/mitchellh/go-libghostty), [x/vt key encoder](https://github.com/charmbracelet/x/blob/main/vt/key.go), [default protocol handlers](https://github.com/charmbracelet/x/blob/main/vt/handlers.go).

### Inferences

- The comparison identified two candidate stacks: broad protocol coverage using libghostty plus PTY and a cell compositor; pure Go using x/vt plus PTY/compositor with a limited protocol baseline. A raw byte relay should preserve ordinary keyboard/paste bytes, while terminal-mode negotiation and mouse-coordinate mapping remain explicit responsibilities. The inspected x/vt defaults do not satisfy modern negotiation without substantive added protocol work. [x/vt handlers](https://github.com/charmbracelet/x/blob/main/vt/handlers.go), [libghostty encoder](https://github.com/mitchellh/go-libghostty/blob/main/key_encoder.go).
- Prefer retaining ownership of host input rather than assuming tview/Bubble Tea event decoding and re-encoding are byte preserving. Their rendering/UI roles are distinct from a child emulator and raw transport. Ultraviolet's support for decoding Kitty keys does not remove x/vt's encoding/negotiation gaps. [Ultraviolet](https://github.com/charmbracelet/ultraviolet/blob/main/README.md), [x/vt key source](https://github.com/charmbracelet/x/blob/main/vt/key.go).
- All observable terminal data should distinguish protocol-reported values from process facts. Neither an OSC CWD string nor a terminal title reveals the child's internal application model; shell prompt metadata requires cooperation. [x/vt CWD comment](https://github.com/charmbracelet/x/blob/main/vt/emulator.go), [libghostty semantic prompts](https://github.com/mitchellh/go-libghostty/blob/main/doc.go).

### Gaps

- This source comparison did not run local build/protocol tests and does not establish arbitrary-app transparency. Source branches may move after this dated review; candidate inspection does not replace version pinning and native-header/binding verification. The [verification record](../../docs/internal/references/verification.md) documents subsequent project checks.
- Render-state/borrowed-view concurrency needs care: libghostty handles are generally not concurrency-safe and borrowed data can expire on mutation. Effects run synchronously and cannot reenter VT writes. [Concurrency contract](https://github.com/mitchellh/go-libghostty/blob/main/doc.go).
- x/vt `osc.go` contains an unexplained `SKIP: Fix typecheck errors` comment. This is a source-quality signal, not evidence that today's module fails to build. [Source](https://github.com/charmbracelet/x/blob/main/vt/osc.go).
- Whole-frame output protocols such as images, palette/title/clipboard side effects and synchronized updates require a compatibility decision; cell access does not prove their faithful outer-terminal behavior.
- Issue turnaround was sampled, not statistically measured. Recent examples: Ultraviolet [#189](https://github.com/charmbracelet/ultraviolet/issues/189) closed after about 12 days and [#177](https://github.com/charmbracelet/ultraviolet/issues/177) after about 22 days; tcell [#1178](https://github.com/gdamore/tcell/issues/1178) after about 4 days and [#1169](https://github.com/gdamore/tcell/issues/1169) after about 23 days. Empty issue-only samples from the first five recently updated closed items for other repos do not establish responsiveness.

## What consumer API style is concise and credible for Go?

### Takeaway

Fluent configuration has an established Go TUI precedent in tview. Keep chaining focused on declarations, then make the execution boundary explicit and error-returning. Protocol/process observation belongs in typed state and callbacks, not dozens of chained getters. [tview example](https://pkg.go.dev/github.com/rivo/tview), [tview application methods](https://github.com/rivo/tview/blob/master/application.go).

### Cited Findings

- tview's own example constructs a box with `NewBox().SetBorder(true).SetTitle(...)` and executes an application with `NewApplication().SetRoot(...).Run()`. Its setters return concrete pointers, while `Run` returns an error. This directly supports the user's preferred chained declaration style without inventing third-party APIs. [Official package example](https://pkg.go.dev/github.com/rivo/tview).
- creack/pty accepts standard `*exec.Cmd`, preserving the familiar Go command/environment/directory model; it does not require shell-string construction. [PTY API](https://pkg.go.dev/github.com/creack/pty).
- libghostty uses functional options for construction and concrete terminal handle methods for operation/inspection, with a documented separation between snapshot/render-state access and side-effect callbacks. [Documentation](https://github.com/mitchellh/go-libghostty/blob/main/doc.go).

### Inferences

- Pre-implementation API recommendation: a concrete builder declares a child command plus header/footer/side information regions, observation hooks, and optional captures, then `Run(context)` performs validation/startup/execution and returns structured child-exit information plus operational error. These are design sketches from this study; the [README API](../../README.md#api) documents the implemented signatures.
- Prefer configuration-only chaining. Declarations should not start a PTY or mutate a host terminal halfway through the chain; the execution method can report configuration errors before child spawn. This is a design recommendation informed by the separation of setters from `Run` in tview, not a claim about implemented go-tui-frame behavior. [tview application](https://github.com/rivo/tview/blob/master/application.go).
- Use standard `exec.Cmd` semantics or a command-plus-argument declaration and expose environment/directory intentionally. Define ownership of an accepted `*exec.Cmd` before implementation; a command cannot be presumed reusable after execution. [Go exec.Cmd contract](https://pkg.go.dev/os/exec#Cmd).
- Observation callbacks should receive stable owned snapshots; retain/copy dependent-library views before concurrent display or storage. Separate a non-consuming observer from an explicit optional input capture whose decision is pass/consume. The user's default-pass requirement is stronger than conventional framework keybindings.

### Gaps

- A fluent API alone does not decide region sizing, state richness, errors, shutdown ownership, or interception semantics. The README needs explicit contracts for those behaviors.
- The consulted Go skill's dependency selection workflow informed the ranked options before dependencies were introduced. The [architecture report](../../reports/TUI%20frame%20architecture%20research.md#selected-native-stack-and-build-time-requirements) records the final selection; the alternatives in this note are not additional selected dependencies.
